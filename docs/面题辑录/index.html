  • BFC是什么

    理解：BFC是"块级格式化上下文"，可以理解为开辟了一个独立的空间，有其独有的布局规则，不会对外部造成影响。可以通过CSS属性开启BFC

    触发BFC的CSS样式：
    根元素，即 HTML
    float: left 或 right 
    overflow: 不为visible，可 auto、scroll、hidden
    display: inline-block、flex、table-cell
    position: absolute 或 fixed

    应用场景：
     1.解决margin重叠（塌陷）
     2.清除内部浮动（通过父盒子开启BFC）
     3.自适应多栏布局（利用BFC不与有浮动的布局重叠）

  • viewport是什么，如何设置

      viewport是用户网页的可视区域，也叫做可视区。手机浏览器是网页放在一个虚拟的窗口中，通常此窗口比手机屏幕宽，用户通过平移缩放查看网页不同的部分。很多设备浏览器默认的viewport宽度是: 980
      移动端浏览器中，window对象有devicePixelRadio属性，官方定为为：设备物理像素和独立像素的比例
          devicePixelRadio（DPR） = 物理像素 / 独立像素


    【设置viewport】head标签中设置meta
    <meta name="viewport" content="width=device-width, inital-scale=1.0, maximum-scale=1.0, user-scalable=no" >
     解析：该meta的作用是让viewport的宽度等于设备的宽度，不允许用户手动缩放，meta中的content各个属性请自行查阅文档，暂不作详细记录。

    有一个结论：在iphone和ipad上，无论给viewport设的宽是多少，如果没有指定默认的缩放值，他们会自动计算这个缩放值，以达到当前页面不会出现横向滚动条的目的，也就是viewport的宽度=屏幕的宽度

    通常一个理想的宽度，可以配置 content="width=device-width, initial-scale=1"，就能实现

  • 选择器权重计算规则

     [选择器]	  					  [权值]
     内联Style				       1000
     ID选择器(X)					    100
     类选择器、伪类选择器、属性选择器(Y)	 10
     类型(标签)选择器、伪元素选择器(Z)	   1

    1.计算ID选择器个数总和(X)，类选择器+属性选择器+伪类选择器个数总和(Y)，标签选择器+伪元素选择器数总和(Z)。

    2. 按照顺序比较对应X Y Z的个数，多的则优先级更高，相同则比较下一个参数，如若都相同则按照就近原则

    3. !important 具有最高优先级。这个属性会打破引入的规则使代码变得难以维护，不到逼不得已不建议采用

  • 回流和重绘是什么，哪些元素会导致

    [回流]：布局引擎会根据各种样式计算每个盒子在页面上的大小与位置
    [重绘]：当计算好盒模型的位置、大小及其他属性后，浏览器根据每个盒子特性进行绘制

    【什么时候会触发回流重绘？】
    · 回流
      0.页面首次加载，必执行（避免不了）
      1.添加、删除可见的DOM
      2.元素的位置发生变化
      3.元素的尺寸发生变化（含：外边距、内边距、边框大小、高度和宽度等）
      4.内容发生变化，如文本变化或图片被另一个不同尺寸的图片替代
      5.浏览器窗口尺寸变化（回流是根据视口的大小来计算元素的位置和大小的）
      特殊：api获取特定属性的值（尺寸相关）时，不一定需要进行回流计算，若这些值没被计算过，会立即回流计算
      offsetTop、offsetLeft、 offsetWidth、offsetHeight、scrollTop、scrollLeft、scrollWidth、scrollHeight、clientTop、clientLeft、clientWidth、clientHeight、getComputedStyle（获取CSS描述，并自动更新）

    · 重绘
    [仅触发重绘的情况]
      1.颜色的修改
      2.文本方向的修改
      3.阴影的修改

    顺口溜：回流一定会导致重绘，但重绘不一定导致回流

    【如何减少回流&重绘？】
     1.合并dom操作，多个css修改，比如合并为class类名样式
     2.将dom离线，再修改样式属性等（display:none）
     3.使用fragment文档片段（createDocumentFragment）
     4.让元素脱离文档流，有自己的图层
     5.在元素布局信息改变时尽量不要查询相关信息（会导致渲染队列强制刷新）
     6.启用will-change，开启css硬件加速，单独让渲染引擎为其实现一个图层（不会牵连主线程，合成线程处理）
     
     
     【合成是什么？GPU加速？】
     "更改一个既不要布局也不要绘制"的属性，渲染引擎会跳过布局和绘制，直接执行后续的合成操作，此过程就叫做`合成`操作。默认情况，标准流中的内容都被绘制在同一个图层(Layer)中，特定的属性会创建一个新的合成层（非主线程，可称为合成线程），这个合成层会占用内存，但可以提高性能（也俗称空间换时间）每个合成层都是单独渲染，并且新图层可以使用`GPU加速`
     · 会形成新的合成层的常见属性
      1.3D transforms
      2.will-change（不错的属性，提前告知浏览器可能会发生的css变化，渲染引擎单独实现合成渲染，不影响它层）
      3.透明度、阴影：opacity
      4.video、canvas、iframe
      5.position:fixed
      6.animation 或 transition 设置了opacity、transform

     · GPU加速
      GPU原本是应用于实现3D CSS的效果，后面随着发展，网站、Chrome的UI都选择了GPU绘制，慢慢发展，Chorme在其多进程架构上也引入了GPU进程。在图形渲染、处理大规模并行计算任务等领域，都得到了GPU加速的应用。Web中，CSS动画尤其是3D变换时、Canvas和WebGL、视频解码编码、WebAssembly模块，都可以利用到GPU加速提高性能。
      通过GPU加速，开发者可以为用户带来更加丰富和流畅的Web体验，同时提高应用程序的响应速度和处理能力。

  • script标签：defer\async 作用

    [默认]: 同步加载和执行脚本，会阻塞HTML的解析

    [async]: 异步加载脚本，加载完成后，会立即执行脚本，并阻塞 HTML 的解析

    [defer]: 异步加载脚本，但会在 HTML 解析完成后执行（DOMContentLoaded事件前），整个过程完全不会阻塞HTML的解析

    区别：
     (1) defer是在 HTML 解析完成后执行，async是在下载完成后立即执行
     (2) 多脚本时，defer会按照加载顺序执行，async则是哪个加载完成先执行哪个

    ps: 将延迟脚本放在页面底部仍是最佳选择。原因：如果脚本放在顶部或者中间，若修改了DOM可能导致重绘和回流，放在底部可以减少不必要的计算。

  • 事件三要素？事件的触发过程是什么，什么是事件代理？

    ✪ 三要素：事件源、事件类型、事件处理程序

    ✪ 事件触发过程有3个阶段：
       1. 捕获阶段：事件会从 window 往目标节点传播，所经过，遇到注册的捕获事件会触发
       2. 目标阶段：事件传递到目标节点，触发目标节点上的注册事件
       3. 冒泡阶段：从事件触发处往 window 传播，所经过，遇到注册的捕获事件会触发

    ps: 如果给同一个节点同时注册了捕获和冒泡事件，事件的触发会根据注册的顺序执行

    ✪ 事件代理：对于动态的子节点，将事件注册到其父节点上，实现事件代理，有效减少DOM绑定注销，节省内存

  • 闭包是什么？可以做什么？有什么问题？

    ✪ 定义：函数内部访问了其他作用域的变量，就是闭包。简单理解就是，函数返回了函数，并且返回的函数访问了外部函数的局部变量

    ✪ 好处
      1.变量一直维持在内存中，可以做缓存
      2.跨作用域访问时，存在局部作用域，有效提高访问速度
      3.避免全局声明变量，占用内存，局部声明，随用随回收

    ✪ 坏处
      1.存在内存泄漏问题，变量一直存在内存中增大了内存消耗。解决：使用后手动赋值null

    延伸应用：模块化、柯里化、dan'li'mo'shi

  • v8垃圾回收机制

    首先要知道为什么需要了解垃圾回收，了解之后，我们就知道什么情况下变量会被回收，什么情况可能出现内存泄漏，我们可以在开发过程中杜绝内存泄漏的隐患，更优雅的书写代码。
    那么说回垃圾回收，什么情况需要回收，通常有一个"可达性分析"的方法，这个方法简单来说就是判断一个变量是否是"可抵达的"，不可抵达也就意味着这个变量不再被需要，那么就会被垃圾回收。

    V8的垃圾回收采用了：分代式垃圾回收策略，将内存分为新生代和老生代，他们也对应了不同的回收方法和策略，对于操作系统64位是1.4G、32位是0.7G。
     【新生代】，一分为二，存储临时的数据，64位是64MB、32位是32MB
       `Scavenge算法` 简述：空间被分为From和To空间，数据会存在From空间，当达到一定比例，就会进行。
       为什么采用copy这样的设计，因为本身内存大小没那么大，目的是牺牲空间换时间，空间每次都有一半闲置，但copy带来的时间是很快的。
     
     【老生代】，连续空间，存储较为长存的数据，64位是1400MB、32位是700MB
       `Mark-Sweep（标记清除）`：从根节点查找可达的变量进行记录，最后将没有标记的变量都清除掉。广度扫描，全停顿标记。
       `Mark-Compact（标记整理）`：先整理再清除，因为整理的时候，可以让标记的数据覆盖掉待清除的垃圾，大大减少清除垃圾的次数。利用：增量标记+三色标记法。


    【新生代 → 老生代】
    新生代本身的内存大小远小于老生代，因其满足一定条件后，新生代中的数据会被存放到老生代当中，意味着，较长时间存放，条件简单来说 1.是否经历过Scavenge算法 2.To空间使用率25%+。

  • js比较时，隐式转换？[]==![] 和 ==! 结果分别是什么

    · === 不会发生转换，直接比较

    · == 会发生转换，再比较
      当两边类型不同时，会尽量将一步步转换为数值（原始类型）进行比较（核心准则有好几条，总结话术）

    []==![] 结果是：true，通过隐式转换：[]==![] -> []==false -> []==0 -> ''==0 -> 0==0 -> true

    {}==!{} 结果是：false，通过隐式转换：{}==!{} -> {}==false -> {}==0 -> NaN==0 -> false

  • 事件循环（Event Loop）

    官方叫Event Loop，浏览器叫Message Loop(消息队列)，是浏览器渲染主线程的工作方式。

      以前简单的将异步事件中的事件循环分为 宏任务 和 微任务，现在这种说法无法满足越来越复杂的浏览器环境，取而代之的是更加灵活多变的处理方式，将各个事件任务分为了不同的队列，同类型的任务放在相同队列中，队列有不同的优先级，由浏览器决定执行哪个队列中的事件，现在有分：微队列(最高优先级)、交互队列（用户鼠标键盘交互）、延时队列（优先级中）

  • 减少 Webpack 的打包时间

    [STAR法则]
    为什么要减少打包时间：项目越大打包的时间也会越长，嗯我们需要尽可能的减少打包的时间
    可以从以下几个方面入手：
    1.『优化loader』
      其中官网就指出，babel-loader 很慢！Babel会将代码转为字符串生成AST，然后转变AST生成最终的代码，我们写的代码越多转换效率也就越低，那么我们就要优化loader的文件搜索范围，具体配置如下：
      1) 配置`exclude`，排除`node_modules`
      2) 配置`include`，只在指定文件夹下查找，例：resolve("src") 只在src文件夹下查找

    2.『多进程构建解析』
     (1) `HappyPack`
       使用 HappyPack 发挥多核CPU电脑的威力，可以让webpack将任务分解成多个子进程同时执行，子进程处理完后再将结果发送给主进程。
    [tip: 由于js是单线程，所以要想发挥多核CPU的能力，只能通过多进程去实现，而无法通过多线程实现。]
      [配置]
      module: {
        loaders: [
          {
            test: /\.js$/
            loader: "happypack/loader" //(1)
          }
        ]
      },
      plugins: [
        new HappyPack({
          loaders: ["babel-loader"], //(2)
          threads: 4 //开启4个子进程
        })
      ]
    （ps: HappyPack作者不从事js工作 已停止维护，官方推出了thread-loader）

     (2) `thread-loader`
      rules: [
        {
          // ...

            "babel-loader",
            {
              loader: "thread-loader",
              options： { //配置参数
                worders: 3, //3个进程数
              }
            }
          ]
        }
      ]

二、渲染模式​

  • SSR

    SSR也就是服务端渲染，页面在后端先获取到数据，然后发回前端注水渲染，如果你不是很熟悉，可以先看一下SSR相关的文章介绍。

  • SSG

    SSG 也就是静态站点生成，在构建时生成静态页面，不同用户访问到的都是同一个页面。

  • ISR

    SSG 的优点就是快，部署不需要服务器，任何静态服务空间都可以部署，而缺点也是因为静态，不能动态渲染，每添加一篇博客，就需要重新构建。所以有了ISR，增量静态生成，可以在一定时间后重新生成静态页面，不需要手动处理。

  • RSC

    Server component 是 React18 提供的能力， 与上面的 SSR 不同，相当于是流式的 SSR。

  • 如何区分 preload 和 prefetch

    preload：是告诉浏览器页面必定需要的资源，在当前页面加载后，浏览器一定会加载这些资源并缓存
    prefetch：异步加载，是告诉浏览器其他页面可能需要的资源，浏览器不一定会使用这些资源

  • http1.1/http2/http3 之间的区别

    1.0 多个请求，多次TCP三次握手，1.1一次TCP

    1. HTTP/1.1
      单一"请求-响应"模型：“1次1份” 一个请求对应一个响应
      默认保持连接（keep-alive）
      缺点：队头阻塞，每个请求和响应的头部信息都在单独的数据包中发送，可能引起头部阻塞问题
      缺乏二进制帧：没有针对数据流的二进制帧，这使得性能优化复杂
      文本协议：HTTP/1.1使用明文文本进行通信，可以被窃听和篡改
      ps: 虽有管线化技术，但是很少使用，因为即使一次性请求多个，仍需要根据请求顺序排队响应，很可能造成其中一个丢包，下一个接口的数据给到这个接口了
      扩展：HTTPS的新增，在HTTP基础上新增了TLS，除TCP三次握手，TLS/1.2新增了四次握手，握手后才能加密通信；那么对于HTTP/1.1，越多的请求来回就意味着越多的未知数,缺点越加明显。

    2. HTTP/2
      多路复用，解决1.1队头阻塞问题（好比送外卖，老板聘请了多个外卖员进行送外卖，不用担心有多个外卖却只有一个外卖员导致送外卖效率很低）
      二进制帧：HTTP/2使用二进制帧格式，请求和响应报文都被划分为了各个不同的帧，分为首部帧和数据帧。还有个流标识符，使帧可以不用按顺序抵达，还能设置帧的优先级，标注流的权重。优点是：减少了数据的传输大小。
      服务器推送：服务器可以主动推送与客户端请求相关的资源，提升页面加载速度。缺点：不小心访问了也会把资源都加载了，可能造成DDoS非对称攻击，存在一个明显的"杠杆"，因此存在安全性问题。
      头部压缩：HTTP/2引入HPACK压缩算法，压缩报文首部，减少了数据传输的大小。
      缺陷：队头阻塞；TCP 与 TLS 的握手时延迟；网络迁移需要重新连接
      
    3. HTTP/3
     传输层采用QUIC: HTTP/3使用基于UDP的传输协议QUIC，这减少了握手时间，提高了安全性
     多路复用和头部压缩：HTTP/3继承了HTTP/2的多路复用和头部压缩的特性，但是在QUIC协议的基础上更高效
     抗头部阻塞：HTTP/3解决了头部阻塞问题，可以更快地传送头部信息（数据帧的概念直接给了QUIC）
     QUIC数据包会添加一个Connection ID 即时wifi->4G IP变了，但是客户端和服务端协商好的连接没变，会识别为同一个连接，避免再次握手。

  • 浏览器输入网址(例: www.baidu.com)，回车后会发生什么？

    【核心详解流程】
     1. 第一步，解析URL，得到协议、域名、端口、文件路径等信息。根据这些信息生成 HTTP 请求消息
     2. DNS查询，首先递归查找本地缓存【浏览器缓存→操作系统缓存→Hosts文件缓存→路由器缓存】，还查询不到，会去查询本地DNS服务器，如果有记录会直接返回，没有的话会通过迭代查询DNS服务器，会先查找根DNS服务器，再查找顶级DNS服务器，最后查找权威DNS服务器，权威dns服务器将查询到的IP告诉给本地DNS服务器，本地DNS再将IP地址返回给客户端。整个过程会尽可能查找到域名对应的真实IP地址，返回给浏览器，找不到则会提示用户相应的内容。
     3. 若得到IP地址，浏览器向IP服务器建立TCP连接（TCP三次握手）
     4. 客户端向服务端发起HTTP请求，访问页面html文件，并获取文件所需的js、css等资源
     5. 关闭TCP连接（TCP四次挥手）当然现在http/1.1支持长连接，很多情况不需要关闭TCP连接，减少连接关闭损耗
     6. 浏览器完成渲染的工作流程，将页面呈现给用户


    【基础流程】
    1. 首先，通过DNS对该网址进行解析，获取到IP地址
    2. 拿到IP地址，与服务器进行TCP连接（TCP三次握手）
    3. 建立TCP连接后，发起HTTP请求
    4. 服务器响应HTTP请求，浏览器获取html代码
    5. 浏览器解析html代码，并请求html代码中的资源（如css、js、图片等）
    6. 服务器结束TCP连接（TCP四次挥手，HTTP/1.1可能长连接不断开，减少断开连接损耗）
    7. 浏览器对页面进行渲染 呈现给用户

  • http缓存方式，强缓存、协商缓存、要说出具体的字段名及用法

    http缓存分为：强缓存 和 协商缓存。通过设置合适的HTTP缓存头，让浏览器缓存资源，减少重复加载相同资源的次数，达到性能优化的目的。
     · 强缓存：不用发请求到服务器，就拿到缓存文件的请求
     · 协商缓存：未命中强缓存，浏览器会向服务器发送资源加载请求。服务器判断浏览器本地资源是否失效，若可以使用，服务器不会返回资源，浏览器继续从缓存加载资源。
     · 无缓冲：协商缓存也未命中的话，服务器会将完整的资源返回给浏览器，浏览器加载新资源，并更新缓存
     
    ✪ 强缓存
     两个关键字段，expires 和 cache-control（优先级更高）
     expires：后面跟着资源的失效实践，这是一个`绝对时间` 缺点:就是当本地时间被修改，服务器和本地时间差异较大时，会导致缓存混乱，所以发展出了：Cache-Control
     cache-control：是一个`相对时间`，例：Cache-Control:max-age=3600 代表资源的有效时间相对本地时间是3600秒，由于是相对时间，所以服务器和本地有没有偏差也不会导致问题。
     
    ✪ 协商缓存
     两个关键字段，Last-Modify/If-Modify-Since 和 Etag/If-None-Match
     Last-Modify：代表资源的最后修改时间，缺点是修改时间因为精确到的是秒，所以可能存在资源更新了，时间却没变；还有可能资源的内容没有变化，但是时间更新了，导致无法使用缓存。于是出现了：Etag
     Etag：资源的唯一ID，只有资源变化了就会更新，解决了Last-Modify的问题
     第一次请求：响应返回 Last-Modify 和 Etag
     第二次请求：请求携带 If-Modify-Since 和 If-None-Match
     协商缓存生效，返回304

    ps: 强缓存适用于静态资源，而协商缓存适用于需要频繁变动的资源。
        网站的缓存设置一般是：入口设置 no-cache 其他资源设置 max-age，这样入口文件会缓存但是每次都协商，保证能及时更新，而其他资源不发请求，减轻服务端压力。

    三级缓存原理
     1.先查找内存，如果内存中存在，从存在中加载
     2.如果内存中未查找到，选择磁盘获取，如果磁盘中有，从磁盘中加载
     3.如果磁盘中未查找到，那就进行网络请求
     4.加载到的资源缓存到磁盘和内存

  • SSE是什么？

    基于http协议的，广泛浏览器都支持，从服务端到客户端的单向、实时 数据传输技术。
    [特点]
     1.单向通信：SSE只支持服务端到客户端的通信，客户端不能给服务端发送数据
     2.文本格式：SSE使用 纯文本格式 传输数据，使用HTTP响应头的 `text/event-stream` MIME类型
     3.长连接：SSE通过保持一个持久的HTTP连接，实现服务端向客户端推送更新，不需要客户端频繁轮询
     4.自动重连：出现连接中断时，浏览器自动尝试重新连接，确保数据流的连续性
     
    [优点]
     1.简单易用：易于实现，无需复杂的配置和建立连接的过程
     2.标准化：基于标准的HTTP协议，具有广泛的浏览器支持
     3.无需握手机制：不需要握手机制，可减少连接的延迟，和其他通信技术相比（如WebSocket）

    [缺点]
     1.单向通信：客户端不能给服务端发送数据
     2.连接维持：SSE要保持连接，可能会造成服务器资源占用
     
    [应用场景]
     1.通知系统（短信、日志等）
     2.实时更新：股票趋势、竞技比分
     3.同步服务器：倒计时、天气、秒杀状态等
    特性/因素SSEWebSockets
    协议基于HTTP，使用标准HTTP连接单独的协议（ws:// 或 wss://），需要握手升级
    通信方式单向通信（服务器到客户端）全双工通信
    数据格式文本（UTF-8编码）文本或二进制
    重连机制浏览器自动重连需要手动实现重连机制
    实时性高（适合频繁更新的场景）非常高（适合高度交互的实时应用）
    浏览器支持良好（大多数现代浏览器支持）非常好（几乎所有现代浏览器支持）
    适用场景实时通知、新闻feed、股票价格等需要从服务器推送到客户端的场景在线游戏、聊天应用、实时交互应用
    复杂性较低，易于实现和维护较高，需要处理连接的建立、维护和断开
    兼容性和可用性基于HTTP，更容易通过各种中间件和防火墙可能需要配置服务器和网络设备以支持WebSocket
    服务器负载适合较低频率的数据更新适合高频率消息和高度交互的场景

  • 区块链是什么？

    可以理解成一种特殊的分布式数据库，其核心观念是去中心化，没有核心的管理员（资本），它是由一个个块（block）组成，每个块又由区块头和区块体组成，区块头包含每个块的独有信息，以及独有hash。比特币的发展就用到了区块链技术，由于计算量庞大每10分钟产生一个区块，比较考验矿工的计算机硬件水平

首先做个自我介绍，我的本科专业是软件工程，主攻方向是前端，兼顾的后端方向主要是NodeJS。大学期间担任学委，负责管理各个组长，主要事宜是学习任务、考试以及考核出题。为了提升自己和体现个人价值，参加过几次竞赛，均有不错的成绩，为了提升技术的熟练度以及掌握业务的实际开发，在学校接过外包和各个组长一起协同开发。以上是个人的大学经历。后面进入公司学习成长，主要的业务方向是B端，大部分都是从0到1独立开发。技术方面的成长有限，主要的收获就是业务的理解和对于抽象业务开发更加熟练。
专业技能方面，精通html、css、js，掌握数据结构与常用算法。开发框架层面 react为主，同时vue3也完全没问题，毕竟最新文档都很详细，新的API很容易上手。对于工程化、性能优化都有一定了解和应用。另外对于SEO、以及高阶技术都有了解，比如webworker、微前端、webAssmebly、SEE等。
个人作品方面，核心作品就是沉词APP，同时也是竞赛和毕设作品。
